# One-job worker container: design and unresolved boundary

## Candidate

A private coordinator holds the durable queue and approval records. A separate worker container receives one job, uses a private PID namespace, has no Docker socket or host namespace, and exits after the job. The coordinator never hands its control secret or Coolify token to the worker. Separate service-level secrets and private storage contain only the worker's required runtime credentials. Lease fencing and uncertain outcomes prevent another job from starting merely because a worker stopped heartbeating. A restart may resume the coordinator, but it must not silently replay an uncertain external action.

Linux kills remaining processes in a PID namespace when namespace PID 1 exits. Docker creates private PID namespaces by default; Docker's stop operation escalates to SIGKILL after its timeout. Compose secrets are granted per service. Sources: [Linux PID namespaces](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html), [Docker PID settings](https://docs.docker.com/reference/cli/docker/container/run/), [Docker stop](https://docs.docker.com/reference/cli/docker/container/stop/), [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

## Why this is not yet sufficient

The guarantee depends on PID 1 actually exiting. If the one-job worker hangs or is compromised, an independent actor must be able to stop its container and verify that the specific worker incarnation has terminated. A coordinator without a Docker socket, host namespace or authorized control-plane capability has no documented way to force that transition. A worker's own promise that it stopped is not independent evidence. Lease expiry fences state writes but cannot prove an old process stopped or prevent it making external requests.

Coolify documents a [per-service-application stop endpoint](https://coolify.io/docs/api/endpoints/service-applications/post-stop-service-application-by-service-and-app-uuid), but its public response schema does not establish that a particular container incarnation and its descendants are gone. Its [MCP setup](https://coolify.io/docs/mcp/setup) says stop/restart needs `deploy` permission and tokens act with their granted team permissions. An independent, narrowly authorized lifecycle controller plus a documented or independently verified incarnation-specific stopped-state check is therefore needed for forced cancellation. An alternative is an operator-controlled stop with independent confirmation; this limits automation. No choice, token, or runtime-control access has been configured.

Compose mounts secrets into each granted container, which separates coordinator-only files from worker-only files; it does not by itself isolate the worker's OAuth access token from code executing inside that same worker. The provider spec sets Codex's documented `shell_environment_policy.inherit="none"` and enables default token exclusions, which limits environment inheritance; this does not by itself prove that same-container processes cannot inspect the app-server or mounted files. A concrete token-broker or sandbox boundary and its compatibility with the documented Codex provider must be designed and tested before treating untrusted agent shell execution as safe. See [Codex shell environment policy](https://developers.openai.com/codex/config-file/config-advanced). The worker must not receive the coordinator's control secret, refresh token, or lifecycle token merely to simplify scheduling.

Coolify scheduled tasks execute commands inside a selected existing container, not a documented one-shot container lifecycle API. Compose uses its own reconciliation rather than Coolify's rolling-update mechanism. See [Coolify scheduled tasks](https://coolify.io/docs/services/operations/scheduled-tasks) and [rolling updates](https://coolify.io/docs/applications/deployments/rolling-updates). Restart policy and external action outcomes must be tested against the selected deployment rather than assumed.

## Local implementation boundary

`runner.queue.JobQueue` provides one-at-a-time claims, expiry to `uncertain`, durable cancellation requests and explicit stop-confirmation hooks. `runner.scheduler.Scheduler` defines a guarded-start interface for an injected supervisor; a callback check alone is not an atomic container start or a cancellation guarantee. The private control socket can enqueue, inspect and request cancellation. These are state/contract primitives, not a container supervisor. The service does not launch the live worker, and no supervisor can assert termination on the basis of a worker-provided boolean. The container, credential broker, lifecycle controller and end-to-end cancellation have not been deployed or validated.
