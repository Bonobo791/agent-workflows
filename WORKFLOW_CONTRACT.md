# Workflow contract (draft)

Workflow implementations live in `workflows/<name>/`. `marketing/` is reserved for the separate marketing session. The shared runner owns SQLite persistence, claims, stage gates, approvals, sessions, artifact versions and events. Workflow definitions provide ordered stage names, dependencies and approval actions; adapters perform external work. Stage input fingerprints determine whether a prior successful result is reusable. Integrations must fail closed when unavailable. External actions require an approval for the exact action and version, and are never performed by a model directly.

This contract is being implemented; coordinate interface changes before integrating marketing.

## Graph interface (prototype, ready for independent testing)

`runner.graph.Definition(name, dependencies, terminal_dependencies)` registers an acyclic stage graph; `GraphStore.register`, `create(run, workflow, task_id=None)`, `claim(run, ttl)`, `renew(run, token, ttl)`, `cancel(run, token)`, `prepare`, `finish`, and `get` persist a run. A claim token fences workers on the same task. `prepare(run, stage, token)` returns an opaque prerequisite revision snapshot; `finish(run, stage, snapshot, status, version, token)` rejects stale input, records the outcome, and invalidates descendants only. Normal edges require `passed`; stages named in `terminal_dependencies` allow `passed`, `blocked`, `failed`, or `unsuitable` dependencies. Marketing review and asset-production stages accept terminal inputs to propagate blocks; only a blocked, failed, or unsuitable outcome can follow a non-passing input. Marketing `assembly` accepts all terminal inputs. `awaiting_review` is a stage outcome, not a terminal dependency outcome. Version inputs must identify all relevant content and policy inputs, not merely a mutable filename. Fresh reviewer sessions and model outputs are the executor's responsibility.

`marketing_definition()` imports the marketing module's declared graph; `engineering_definition()` registers a linear graph. These APIs are state primitives, not an authorization boundary or a complete runner. They do not execute the marketing gates, verify artifacts, authenticate callers, collect task data, or approve external actions. A production executor must enforce those checks before recording a passing stage. The old sequential `runner.store.Store` is a separate prototype and has not yet been reconciled with the graph store. No action is authorized simply because a stage record exists.

Asset adapter seam: a future adapter receives a versioned brief and produces project, render and independent verification references. Missing adapter, failed verification, or missing references must result in `blocked`. No provider or paid generation is configured.

`begin_attempt(run, stage, input_version, token, max_attempts)` persists a bounded attempt before execution. Its initial outcome is uncertain; `resolve_attempt(run, stage, input_version, token, outcome)` requires a confirmed `failed`, `completed`, or `not_executed` outcome before another attempt. This is a persistence primitive; the caller must establish the actual outcome and prevent untrusted callers from resolving it. Cancellation invalidates the run's claim and rejects late writes. It does not itself stop a child process. `runner.process.ManagedProcess` provides best-effort process-group termination for a directly managed process; it is not a sandbox or protection from escaped descendants. Runtime isolation and process cancellation must be integrated before live execution.

`runner.artifacts.ArtifactStore` stores private blobs by SHA-256, creates files without replacement and verifies contents on every read. Files are owner-readable only; this detects tampering but does not make storage immutable against its owner, and consumers must verify the same bytes they use. Asset verification and editorial/rights review remain separate gates.

## Synthetic service integration

`runner.service.Service(root)` wires both registered graphs, private artifact storage, human freeze approvals and pure marketing/engineering gates for trusted local synthetic evidence. It supports `create`, `claim`, `release`, `approve`, `complete` and `close`. Marketing assembly includes blocked asset status. Changed reviewed content invalidates its freeze and requires a new approval. An explicitly configured local skill resolver hashes and loads named skills; missing or changed upstream skills invalidate results. The service does not yet fetch tasks, invoke Codex, independently verify model-provided evidence, or execute GitHub actions. Its evidence interface is for synthetic fixtures and is not a production approval system. `runner.worker` exposes a secret-authenticated owner-only Unix socket with live execution disabled and no network listener.
